# 项目概述：浅草寺抽签插件-PRO

## 1. 项目简介
基于 AstrBot 框架的模拟日本浅草寺抽签功能的聊天机器人插件，用户可通过命令随机抽取签文、查看运势，并借助大语言模型获得签文解读。

## 2. 技术栈
- **框架**：AstrBot（插件化机器人框架，asyncio 异步模型）
- **语言**：Python
- **依赖库**：异步处理、定时任务、字体渲染、json 文件存储
- **LLM 集成**：支持调用大型语言模型进行智能解签（通过 @llm_tool 装饰器）
- **数据存储**：本地 JSON 文件持久化（用户抽签状态、次数统计）

## 3. 架构设计与关键决策
- **异步优先**：插件运行在 asyncio 事件循环中，使用 `asyncio.Lock` 保证并发安全
- **数据层分离**：用户状态存储于独立 JSON 文件，签文数据在 `sensoji_data.py` 中静态定义
- **双路径解签**：支持普通命令 `/解签` 和 LLM 工具调用 `explain_fortune_tool`，上下文对象来源不同
- **定时清理**：异步定时任务清理临时生成的签文图片文件，避免资源堆积
- **跨平台适配**：通过 `event.get_sender_id()` 获取用户标识，需注意桥接场景下 ID 一致性问题

## 4. 已知问题与注意事项
- **并发安全风险**：现有锁粒度覆盖部分读-改-写操作，但写操作时可能无锁保护，存在竞态条件
- **同步 I/O 阻塞事件循环**：大量使用 `open` + `json.dump/load` 进行文件操作，无 `aiofiles` 或 `run_in_executor` 封装
- **错误处理缺失**：`load_data()` 等函数未捕获 JSON 解析异常（空文件/损坏格式），可能导致插件崩溃
- **冗余 I/O**：多处重复从磁盘加载相同数据，尤其在持有锁的上下文中
- **持久化不一致**：不同保存函数（如 `save_data` vs `save_change_counts`）对 `fsync` 的使用不一致
- **用户状态键设计**：推荐使用 `unified_msg_origin + sender_id` 复合键，而非单一 ID，以避免跨平台桥接时的状态丢失
- **LLM 工具调用上下文差异**：`@llm_tool` 调用链中的事件对象可能被池化或序列化重建，导致 ID 字段变化

## 5. 审查中发现的重要模式
- **手动文件管理 vs 异步安全**：直接使用同步 I/O 在 asyncio 环境中是隐藏性能隐患
- **重复的文件加载模式**：缺少统一数据访问层和缓存机制
- **跨函数耦合**：外层已加载的数据被内层函数再次从磁盘加载（如 `get_or_generate_result` 调用 `load_data`）
- **注释代码残留**：保留大量被注释的旧逻辑，干扰阅读

## 6. 团队约定与规范
- **命令前缀**：`/抽签`、`/抽签帮助`、`转运`、`/解签`，支持自然语言触发
- **配置规范**：使用 JSON Schema 定义配置项（`_conf_schema.json`）
- **代码审查规则**（已沉淀）：
  - R-001：异步插件中的同步文件 I/O 应替换为 `aiofiles` 或 `run_in_executor`
  - R-002：所有 `load_data` 必须有 try-except 处理 JSON 解析错误
  - R-003：持有锁的上下文中避免重复从磁盘加载数据
  - R-004：所有持久化函数必须使用一致的 flush + os.fsync
  - R-005：docstring 不应包含代码演化历史
- **降级设计原则**：对 LLM 依赖的功能须有基于规则的兜底方案，避免静默失败
