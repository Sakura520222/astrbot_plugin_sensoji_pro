## 常见代码问题和审查要点

### 并发与异步安全
- 异步插件中使用同步文件 I/O（open/read/write）会阻塞事件循环，应替换为 aiofiles 或 run_in_executor
- 锁的粒度必须覆盖所有读-改-写操作，且锁内避免执行大 I/O
- 检查是否存在死锁风险：锁内调用的方法是否间接触发同一把锁
- 使用 async with lock 确保异常时锁被释放

### 持久化可靠性
- 所有 save_* 函数必须使用一致的 flush + os.fsync 保证数据完整性
- load_data 操作必须有 try-except 处理 JSON 解析错误，返回安全的默认结构
- 多方法共享的数据应通过参数传递而非重复从磁盘加载

### 代码规范
- docstring 不应包含代码演化历史或旧实现对比，此类信息应放入 commit message 或 PR 描述
- 删除注释代码残留，避免后续理解困难
- 文件末尾应有换行符

## 近期审查模式总结

- 全量审查能发现增量审查遗漏的跨函数不一致问题（如两个 save 函数实现差异、已加载数据又被重复加载）
- 涉及核心数据流或并发安全的 PR，即使变更量小也应触发全量审查
- 跨平台桥接类插件必须检查 event.get_sender_id() 的来源一致性，推荐使用复合键

### 经验教训
- 并发审查要点：锁粒度、I/O 是否在锁内、异常安全性
- 重构类 PR 重点：新旧行为等价性、新依赖、测试同步
- LLM 依赖分析必须有降级方案（超时/失败 → 规则降级 → 人工标注）
- “状态丢失”类 Issue 优先检查：用户 ID 获取方式、状态绑定维度（group_id+user_id）、全局变量 vs 持久化存储
- LLM 工具函数与普通命令的上下文差异：事件对象可能被序列化重建导致 ID 字段丢失
