## 2. 发现的模式

- **手动文件管理 vs 异步安全**：项目直接使用 `json.dump` + `os.fsync` 而非异步安全库（如 `aiofiles`）。在 `asyncio` 环境中，同步 I/O 会阻塞事件循环。虽然当前可能可接受，但这是一个隐藏的性能隐患。
- **大量重复的文件加载模式**：多处调用 `load_data()` 而缺少缓存或依赖注入，导致冗余 I/O。这反映出项目缺少统一的数据访问层。
- **注释代码残留**：虽提到清理注释代码，但未完全评估所有被注释的旧逻辑，可能导致后续理解困难。

## 4. 经验教训

- **并发代码审查的要点**：
  - **锁的粒度**：检查锁是否覆盖了所有读-改-写操作。
  - **I/O 是否在锁内**：锁内进行大 I/O 会降低并发性能，应移至锁外。
  - **异常安全性**：加锁后若抛出异常，锁是否确保释放（`async with lock` 安全）。
- **重构类 PR 的审查重点**：
  - 新旧行为是否等价（尤其是错误路径和边界条件）。
  - 是否引入了新的依赖或改变了异步模型。
  - 测试是否同步更新。
- **对“全量审查”的再思考**：全量审查的价值在于发现跨函数/跨模块的重复逻辑、不一致的编码约定以及低频但致命的并发问题。本次审查中冗余 I/O 的发现即是典型案例。
