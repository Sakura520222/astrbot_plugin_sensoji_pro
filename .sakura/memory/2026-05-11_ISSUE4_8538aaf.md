## Issue #4 深度反思

### 1. 分类与优先级准确性

- **分类问题**：当前分类为 `other`，但实际应归类为 `bug`。用户明确描述了预期行为（抽签后应能解签）与实际行为（LLM 提示未抽签）的差异，这是典型的功能性缺陷。
- **优先级判断**：当前 `medium` 较合理。该问题影响核心抽签-解签流程的用户体验，但存在临时规避手段（重试或检查抽签状态）。
- **关键词匹配失误**：AI 调用超时导致分析中断，系统错误地将“AI 分析失败”作为 Issue 分类依据，而非基于 Issue 内容本身。**这是分析流程的设计缺陷**：应在 AI 分析失败时回退到规则分类（如关键词“抽签/解签”+“提示”→ bug）。

### 2. 标签推荐质量

- **缺标签**：至少应推荐 `state-loss`、`session`、`llm-context`。根据项目记忆中的经验教训，“状态丢失”类 Issue 是已知高频模式。
- **置信度评估缺失**：当前输出没有标签置信度，无法判断是否需要人工复核。
- **建议**：对“AI 分析失败”的输出应强制添加 `needs-human-review` 标签，并保留原始内容供人工判断。

### 3. 可行性判断质量

- **严重问题**：`无法评估` 是因为 AI 超时，而非真正不可复现或缺乏信息。日志已明确显示：
  - 用户 `/抽签` 后系统 Prepare to send（发送成功但内容被截断）
  - 随后 `/解签` 时 LLM 提示未抽签
- **根本原因推测**（基于项目记忆）：
  1. 抽签状态存储的 key 可能仅用 `user_id`，但跨平台桥接中 `event.get_sender_id()` 返回的值可能与解签时不一致（序列化重建丢字段）
  2. 抽签后状态保存到全局变量而非持久化，重启或并发请求导致丢失
  3. LLM 工具函数与普通命令的上下文差异，解签时 LLM 拿到的 session 中不含抽签记录
- **真正可行性**：可修复，工作量约 2-4 小时，需检查状态绑定逻辑并增加日志。

### 4. 重复检测准确性

- **状态**：未检测到重复。
- **评估**：由于 Issue 标题仅为 `bug`，内容摘要截断，AI 分析又失败，系统确实难以匹配。但项目记忆中已有“状态丢失”类经验，**理论上应将此 Issue 与同类模式关联**。
- **改进方向**：建立基于“错误症状”的模糊匹配库（如“仍然提示我要先X”→“state-loss”类已知问题），即使标题不完整也能触发提示。

### 5. 标题改写适当性

- **当前状态**：无建议标题。
- **必要性**：原标题 `bug` 信息量为零，必须改写。建议标题：`执行 /解签 时 LLM 错误提示“未抽签”，尽管用户已执行 /抽签`
- **原则**：当原始标题为无意义词（bug/报错/问题）且 AI 能理解内容时，应主动生成有信息量的标题，并标记 `title-auto-generated`。

### 6. 经验教训

| 要点 | 说明 |
|------|------|
| **AI 分析必须有过期/超时降级** | 900 秒超时不应用于生产分析，应设 30 秒 → 失败后触发规则分类 + 人工标注队列 |
| **日志截断问题** | Prepare to send 后的消息内容未打印完整，导致无法确认抽签返回内容。建议要求插件在关键流程打印结构化日志（含状态 key、user_id 复合键） |
| **状态丢失类 Issue 的快速定位路径** | 1. 检查 user_id 获取方式 2. 检查状态绑定维度（是否 group+user）3. 检查存储是否持久化 4. 检查 LLM 工具函数是否重建上下文 |
| **“other”分类的触发条件应收紧** | 仅在确认非 bug/非功能请求/非文档/非性能时使用。当前被 AI 失败错误触发，应加前置判断 |
| **AI 分析失败本身应生成独立 Issue 元数据** | 记录失败原因（超时/解析错误/API 错误），用于监控分析系统的健康度 |

**一句话总结**：本次分析的核心问题是 **AI 调用超时被错误地当成了 Issue 的分类依据**，而非对用户实际问题的分析。应在流程层区分“分析失败”和“分析结果为 other”。
