## Issue #4 分析反思

### 1. 分类与优先级准确性

- **分类问题**：当前分类为 `other`，属于分析失败的兜底结果。实际应归类为 **“状态/上下文问题”** 或 **“逻辑缺陷”**。
- **根本原因**：AI 调用超时（900秒）导致分析失败，而非 Issue 本身无类别。这暴露了分析链路的问题：**当 LLM 分析失败时，应回退到规则分类并标记 `needs-human-review`**，而不是简单标记为 `other`。
- **优先级判断**：`medium` 合理。用户无法完成“抽签→解签”核心流程，属于中等严重性；但不影响插件启动或其他命令。

### 2. 标签推荐质量

- 当前没有输出任何标签，属于信息缺失。
- **应推荐的标签**：
  - `state-management`（状态绑定问题，解签找不到抽签记录）
  - `user-id`（可能是跨平台 ID 来源不一致）
  - `need-log`（从日志看只有时间戳，缺少关键调试信息如实际获取到的 user_id）
- **置信度**：高。基于项目记忆中的“状态丢失”快速定位路径。

### 3. 可行性判断质量

- 当前为“无法评估”，这实际上是**分析工具自身的失败**，而非对 Issue 修复难度的评估。
- **正确判断**：可行性应为 **高**。典型问题路径清晰：
  1. 检查 `/抽签` 保存状态时使用的 user_id 获取方式
  2. 检查 `/解签` 读取状态时使用的 user_id 获取方式
  3. 确认是否一致（如一个用 `user_id`，另一个用 `group_id+user_id`）
- **工作量**：较小（约 30-60 分钟），通常涉及 1-2 个文件的几行代码修改。

### 4. 重复检测准确性

- 当前“未检测到重复”——在无有效 Issue 内容分析的情况下，这个结论**不可信**。
- 实际应在分析前先基于标题+关键词做本地规则匹配（如搜索“解签 未抽签”、“状态丢失”等模式），而非完全依赖 LLM 相似度检索。

### 5. 标题改写适当性

- 原标题 `bug` 属于无信息量标题。
- 建议改写的标题：**“解签时提示未抽签，但实际已执行过抽签命令”**
- 核心信息保留完整，且指明了错误的可复现场景。

### 6. 经验教训

| 要点 | 建议 |
|------|------|
| LLM 分析超时不等于 Issue 无法分类 | 必须设置硬超时（如 30 秒），超时后回退到规则分类 + 规则标题生成 |
| “状态丢失”类 Issue 的盲检模式 | 无需 LLM 即可给出初步诊断：检查 user_id 获取一致性、持久化 vs 内存、复合键格式 |
| 日志信息不足是模式缺陷 | 建议插件在保存状态时打印 `[DEBUG] save for user_id=xxx`，读取时打印 `[DEBUG] load for user_id=xxx, found={true/false}` |
| 分析报告中不应出现“AI调用失败”作为结论 | 这是一个系统级故障，不应透出给用户作为 Issue 分析结果。正确做法：标记 `analysis-failed`，保留原始内容，转人工 |

**核心原则**：Issue 分析工具的健壮性不能依赖于 LLM 的成功调用。必须有规则引擎兜底，特别是对于“状态丢失”这种高频、低复杂度的问题模式。
